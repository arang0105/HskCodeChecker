# HS코드 분류 검증 보조 시스템

수입 물품의 물품설명을 넣으면 **HS 10자리 세번 후보와 그 근거가 된 과거 결정례**를 함께 돌려주는 시스템입니다.

관세 품목분류는 같은 물품을 두고도 판단이 갈립니다. 그래서 목표를 "정확한 자동 분류기"가 아니라
**"사람이 검토할 지점을 짚어주는 보조 도구"** 로 잡았습니다.

---

## 이 시스템은 얼마나 맞히나

**문제 난이도에 따라 크게 다릅니다.** 
물품의 품목분류의 난이도에 따라 정답률이 달라져 두개의 숫자로 정리했습니다.

| 어떤 문제인가 | 1순위 정답 (앞 6자리) | 1순위 정답 (10자리 전체) | 후보 3개 안에 정답 |
|---|---|---|---|
| **보통 건** 20건<br>선례가 명확한 일반 사전심사 | **85.0%** | **80.0%** | 100% |
| **어려운 건** 30건<br>전문가끼리도 판단이 갈려 협의회에 올라간 사례 | **56.7%** | **50.0%** | 80.0% |

같은 시스템내에서 확인한 난이도가 다른 두 종류의 문제입니다.

### 「어려운 건 30건」은 봉인해 둔 시험 문제입니다

이 30건은 **만드는 동안 한 번도 열어보지 않았습니다.**

만들면서 계속 보는 문제로 점수를 재면 실력이 아니라 **암기 테스트를 하게 됩니다.**
고치고 → 점수 보고 → 또 고치다 보면, 그 점수는 "이 시스템이 새 물품을 얼마나
맞히는가"가 아니라 "그 문제들에 얼마나 맞췄는가"가 됩니다. 그래서 30건을 따로
떼어 **열어보는 횟수를 2회로 규칙으로 정했고, 2회 테스트 했습니다.**

봉인한 보람이 있었습니다. **만들면서 계속 봤던 연습용 29건에서는 75.9%가 나왔는데,
봉인을 열어보니 56.7%였습니다 — 19%p 차이입니다.** 봉인하지 않았다면 75.9%를
제 실력으로 착각했을 것입니다.

그리고 이 30건은 **어려운 쪽으로 치우쳐 있습니다.** 전부 협의회 사례, 즉
사람 전문가들끼리도 의견이 갈려서 논의에 올라간 건들입니다. 그래서 56.7%는
**실무 평균이 아니라 가장 어려운 구간의 숫자**로 읽어야 합니다.

**두 번 열었고 두 번 다 같은 답이 나왔습니다.** 두 번째로 열었을 때 1순위 정답
여부(6자리·10자리)와 최종 10자리 코드가 **30건 전건 일치**했습니다. 자세한 대조는
아래 [측정](#이-프로젝트에서-가장-신경-쓴-것--측정)에 있습니다.

### 「보통 건 20건」에는 단서가 세 개 붙습니다

- **이 20건은 봉인 문제가 아닙니다.** 분류과정을 고칠 때마다 "쉬운 것도 망가뜨리지
  않았나" 확인하려고 돌려 보는 감시용이라 여러 번 봤습니다
- **이 20건은 후보 생성 단계([1])만으로도 이미 85.0%였습니다.** 즉 보통 건에서 이
  시스템의 역할은 "정확도를 올린다"가 아니라 **"맞던 걸 안 망가뜨린다"** 입니다
  (재정렬이 맞게 바꾼 건 1 / 틀리게 바꾼 건 1 — 순증감 0)
- 따라서 85.0%는 **감을 잡기 위한 참고 수치**입니다.
  이 문서가 대표값으로 인용하는 숫자는 **어려운 건 56.7%** 쪽입니다

### 아무 보조 없이 물었을 때와 비교하면 (연습용 29건 기준)

| 지표 | 맨몸 성적 | 현재 |
|---|---|---|
| 1순위 정답률 (앞 6자리) | 44.8% | **75.9%** |
| 1순위 정답률 (10자리 전체) | 13.8% | **69.0%** |
| 6자리를 맞힌 건 중 10자리까지 맞힌 비율 | 31% | **90.9%** |

**맨몸 성적**은 같은 물품설명을 아무 보조 없이 LLM에 그대로 물었을 때의 값입니다
(`gemini-3.1-pro-preview`, 검색 차단, 건별 새 세션, 손으로 측정한 29건).

**이 표는 연습용 29건입니다. 위의 56.7%와 나란히 놓고 읽으면 안 됩니다.**
어려운 건 30건에는 맨몸 성적이 없습니다 — 봉인해 둔 문제라 손으로 재지 않았기
때문입니다. 그래서 **개선 폭은 연습용에서만 말할 수 있고, 실제 성능은 봉인을 연
56.7% / 50.0% 로 봐야 합니다.** 둘을 한 표에 섞으면 개선 폭이 실제보다 커 보여서
표를 나눴습니다.

> 맨몸 성적 6자리는 처음 41.4%로 기록했다가 **44.8%로 정정했습니다.** 측정표의 O/X 계산에
> 셀 오류가 있어 1건이 오답으로 세어져 있었습니다. 제 개선 폭이 3.4%p 줄어드는 정정입니다.
> 경위는 [EXPERIMENTS.md](EXPERIMENTS.md)에 있습니다.

## 어떻게 동작하는가

```
물품설명
  ├─[0] 게이트       물품이 특정되지 않으면 되묻고 멈춘다
  ├─[1] 후보 생성    LLM에 6자리 후보 3개를 받는다
  ├─[2] 결정례 검색  물품설명 임베딩으로 유사 결정례 top-5 (검색 대상 5,872건)
  ├─[3] 재정렬       후보 + 결정례를 함께 주고 순위를 다시 판단
  └─[4] 세번 확정    확정된 6자리 아래 10자리 목록에서 선택
출력: 코드 + 근거 결정례 + 확신도 + 사람이 확인할 포인트
```

설계의 출발점은 맨몸 성적을 재다가 나온 사실 하나였습니다.

> **모델은 이미 정답의 86.2%를 후보 3개 안에 담고 있었다.**
> 부족한 건 생성 능력이 아니라 **순위**다.

그래서 새 코드를 만들지 않고 순위만 고치는 [3]을 1순위로 두었고, [3]에는
**후보 밖 코드를 만들지 못하게** 제약을 걸었습니다. 그래야 개선이 재정렬 덕인지
후보 확장 덕인지 구분됩니다.

[4]는 관세청 공식 HS부호 목록(11,327개)에서 6자리 하위 항목만 뽑아 선택지로 줍니다.
목록을 주기 전에는 모델이 10자리를 **지어냈습니다.**

참고하는 과거 결정례 5,872건은, 수집한 5,921건에서 **시험에 쓴 문제들을 뺀 수**입니다
(연습용 29건 + 보통 건 20건). 시험 문제의 정답이 참고 자료에 들어 있으면 그대로
베끼게 되므로 빼 두었습니다.

위 숫자를 만든 구성은 다음과 같이 고정돼 있습니다. **배포한 앱과 인용한 숫자가
같은 시스템이어야 하므로**, 이후 변경은 "봉인을 연 뒤의 변경"으로 따로 적습니다.

| 항목 | 값 | 왜 이 값인가 |
|---|---|---|
| 모델 | [3]만 `gemini-3.1-pro-preview`, 나머지는 `gemini-3.7-flash` | 모델 급이 결과를 가른 단계는 [3]뿐이었습니다 |
| temperature | 1.0 | 0.2로 낮춰 봤지만 정확도가 내려가 기각했습니다 |
| 검색 top_k | 5 | 8·20으로 늘려도 [3]이 쓸 수 있는 건수가 늘지 않았습니다 |
| 결정례 입력 | 결정사유 600자 포함 | 코드만 주면 정확도가 떨어집니다 (아래 참조) |

## 정보가 부족하면 답하지 않는다 — [0] 게이트

실무에서 관세사에게 도착하는 입력은 `D-100 Wash Solution` 같은 품명 한 줄인 경우가 많습니다.
맨몸 성적을 잴 때 모델은 그런 입력에도 **28건 중 27건을 되묻지 않고 답했습니다**(정보부족 인지율 3.6%).

| 입력 | 되물어야 하는가 | 맨몸 성적 | 현재 |
|---|---|---|---|
| 품번만 있는 입력 7건 | 되물어야 함 | 14.3% | **57.1%** |
| 품명이 명확한 입력 21건 | 되물으면 오작동 | 0% | **4.8%** |
| 상세 물품설명 49건 | 되물으면 오작동 | — | **2.0% (1/49)** |

되묻기의 목적은 정확도가 아니라 **안전성**입니다. 맨몸 성적을 잴 때 상세 설명과 품명 원문 사이에
유의미한 성능 차이가 없었기 때문에(상세 설명만 맞은 3건 / 품명 원문만 맞은 4건), 되묻기로
정확도가 오를 것이라 기대하지 않았습니다. **확신에 차서 틀린 답을 주지 않는 것**이 전부입니다.

목표는 70%였고 **57.1%로 미달했습니다.** 1건 차이입니다. 통과된 3건 중 2건은 레이블 쪽이
의심스럽지만, 채점 기준을 사후에 유리하게 바꾸지 않고 57.1%를 그대로 인용합니다.

두 가지를 설계에 박아 두었습니다.

- **파싱에 실패하면 통과시킵니다.** 안전장치가 고장 났다고 도구 전체가 멈추면 안 됩니다
- **정확도 측정에는 넣지 않습니다.** 게이트가 섞이면 "재정렬 전 / 재정렬 후" 분해가 무너집니다

덤으로, 상세 물품설명에서 게이트가 되물은 1건은 오작동이 아니라 **문제 자체의 결함**이었습니다.
물품설명이 `"상기 성분으로 혼합된..."`인데 그 "상기 성분"이 입력에 없었습니다 —
발췌할 때 성분표가 잘려 나간 건이고, 게이트는 그 지점을 정확히 물었습니다.

## 이 프로젝트에서 가장 신경 쓴 것 — 측정

정확도를 올린 것보다, **올랐다는 사실을 어떻게 증명했는가**에 더 많은 시간을 썼습니다.

**개선분을 겹쳐 세지 않습니다.** 44.8% → 75.9%를 통째로 "재정렬 효과"라고 부르지 않았습니다.
아래는 연습용 29건 기준입니다.

| 단계 | 1순위 정답률 (앞 6자리) | 순수 기여 |
|---|---|---|
| 맨몸 성적 | 44.8% | — |
| + 채점 자동화 · 답변 형식 고정 | 55.2% | 프롬프트·출력형식 |
| + [3] 재정렬 | 72.4% | **+5건** |

**재정렬을 안 했을 때의 점수를 같은 실행 안에서 함께 잽니다.** 매번 다른 날 잰 숫자와
비교하면, 모델 답변이 원래 조금씩 흔들리는 부분까지 "개선"으로 세어집니다.

**비율이 아니라 건별로 대조합니다.** 비율만 같고 맞힌 건이 다를 수 있어서, 매 실행마다
새로 맞힌 건 번호와 새로 틀린 건 번호를 출력합니다.

**봉인은 2번만 엽니다.** 어려운 건 30건은 참고 자료에서도 빼 두고, 열어보는 횟수를
규칙으로 제한했습니다. 연습용 숫자에 맞춰 계속 고치다 보면 그 숫자를 실력으로
착각하게 되기 때문입니다 (위 [결과](#이-시스템은-얼마나-맞히나) 참조).
**2회를 다 썼으므로 더 열지 않습니다** — 이후 분류과정을 고쳐도 그 개선을
이 30건으로 판정하지 않습니다.

**두 번째로 열 때는 같은 조건으로 다시 돌렸습니다.** 조건을 하나라도 바꾸면 차이가
분류과정 때문인지 조건 때문인지 알 수 없게 되므로, 모델·설정·프롬프트를 전부 고정했습니다.

| 대조 항목 | 1회차와 다른 건수 |
|---|---|
| 1순위 정답 여부 (앞 6자리) | **0 / 30** |
| 1순위 정답 여부 (10자리 전체) | **0 / 30** |
| [4]가 고른 최종 10자리 코드 | **0 / 30** |
| [3]이 매긴 **후보 순서** | 3건 — 전부 2·3순위끼리 교체, 1순위는 전건 동일 |

재정렬이 맞게 바꾼 건(T4·T14·T20)과 틀리게 바꾼 건(T5·T21)까지 같았습니다.
답이 조금씩 흔들리게 설정돼 있는데도 결론이 한 건도 바뀌지 않았습니다.

단, 이건 **[3]과 [4]의 재현**이지 분류과정 전체의 재현이 아닙니다. [1] 후보는
1회차에 받아 둔 것을 그대로 썼습니다(30건 전건). 앱은 [1]도 매번 새로 부릅니다.

**고칠 때마다 "쉬운 것도 망가지지 않았나" 확인합니다.** 위에서 말한 **보통 건 20건**이
그 감시용입니다. 연습용 29건과 겹치지 않게 뽑아 참고 자료에서도 빼 두고, 분류과정을
건드릴 때마다 맞게 바뀐 건과 틀리게 바뀐 건을 셉니다. 비율이 유지돼도 틀리게 바뀐 건이
나오면 변경을 되돌립니다. 어려운 문제로만 재면 **쉬운 걸 망가뜨리고도 모릅니다.**

**정답 베끼기를 막습니다.** 시험에 쓴 결정례가 참고 자료 안에 있으면 모델이 정답을
그대로 베낍니다. 기본 동작은 제외이고, 일부러 포함시키는 건 "베낄 수 있으면 얼마나
오르는가"의 격차를 재는 용도로만 켭니다.

## 정확도보다 쓸모 있을지 모르는 발견

모델은 답과 함께 **자기 확신도(high / medium / low)** 를 스스로 매깁니다.
그 라벨이 실제 정답률을 가릅니다 — 다만 **한쪽 방향으로만 믿을 수 있습니다.**
봉인을 두 번 열어 보고 알게 된 것입니다.

| 확신도 | 연습용 29건 | 어려운 건 1회차 | 어려운 건 2회차 |
|---|---|---|---|
| high | 19/21 (90.5%) | 17/24 (70.8%) | 17/26 (**65.4%**) |
| medium | 2/6 | **0/5** | **0/3** |
| low | 0/2 | **0/1** | **0/1** |

**high가 아닌 답은 어려운 건에서 10건 전부 오답이었습니다**(1회차 6건 + 2회차 4건).
세 번 모두 재현됐고, 이게 이 절에서 가장 단단한 사실입니다.

반대 방향은 그렇지 않습니다. 2회차에서 **오답 3건(T5·T21·T28)이 medium에서
high로 올라왔습니다.** 최종 코드는 30건 전건 그대로였는데 **확신도 라벨만
흔들린 것**이라, high의 정답률이 70.8% → 65.4%로 떨어졌습니다.

> **확신도는 거르는 장치이지 보증이 아닙니다.**
> high가 아니면 거의 확실히 틀렸고, high라도 3건 중 1건은 틀립니다.

운영 규칙을 여기에 맞춰 적었습니다 — *"high가 아니면 반드시 확인"* 은 유지하되,
*"high면 안전하다"* 로 읽히지 않도록 앱 화면에도 두 문장을 함께 띄웁니다.
한 번만 재고 90.5%를 인용했다면 이 비대칭을 못 봤을 것입니다.

또 하나, [4]는 정확도만 올린 게 아니라 **답을 재현 가능하게** 만들었습니다.

| | 이전 | 현재 |
|---|---|---|
| 6자리가 3회 일치 | 90% | 80% |
| **10자리가 3회 일치** | **60%** | **80%** |

이전에는 6자리가 같아도 10자리가 흔들렸습니다. 지금은 두 숫자가 같습니다 —
**6자리만 정해지면 10자리는 더 이상 흔들리지 않습니다.**

> 단, **'이전'과 '현재'를 서로 다른 모델로 쟀습니다**(pro / flash). 비싼 모델의
> 일일 호출 한도(250회) 안에서 이 재측정(90회)과 봉인 최종 열람을 같은 날 돌릴 수 없어
> 열람 쪽을 택했습니다. 같은 조건으로 맞춘 값이 아니므로 그대로 인용하지 않습니다.
> 대신 같은 모델로 확인한 재현 근거는 위의 **어려운 건 30건 전건 일치** 쪽입니다.

### 재정렬은 결정례의 코드를 베끼는 게 아니라 판단 근거를 읽는다

프롬프트를 줄일 여지를 보려고 결정례에서 **결정사유(왜 그렇게 분류했는지)를 빼고
코드만 남겨** 같은 실행을 다시 돌렸습니다. 입력 토큰은 42.3% 줄었지만 6자리는
72.4% → 69.0%로 떨어졌습니다.

차이가 난 1건은 두 조건 모두 정답 결정례를 검색해 왔고, **그 결정세번도 프롬프트에
똑같이 들어 있었습니다.** 코드만 본 쪽은 순위를 그대로 두었고, 결정사유를 읽은 쪽만
1위를 바꿔 정답이 됐습니다. 양쪽 다 확신도는 `high`였습니다.

토큰을 42% 아끼고도 **채택하지 않았습니다.** 일일 한도가 토큰이 아니라 요청 수
기준(250 req/day)이라, 입력을 줄여도 하루 처리량은 1건도 늘지 않기 때문입니다.

## 알려진 한계

- **시험 문제가 이미 공표된 결정례입니다.** 인터넷을 검색할 수 있는 모델이라면
  정답을 찾아내므로 점수가 부풀려집니다. 검색을 차단해 통제했고(결정례를 인용한 답변
  0건 확인), 실제 목표인 **아직 결정이 안 난 신규 품목**의 대리 지표로 씁니다.
- **표본이 작습니다.** 연습용 29건, 어려운 건 30건, 보통 건 20건입니다.
  1~2건이 3%p를 움직입니다.
- **어려운 건에서 목표(6자리 60%)에 미달했습니다.** 56.7%로 1건 차이입니다.
  목표를 낮춰 기록하고 다음 단계로 넘어갔습니다 — 미달 사실과 원인 분석도 산출물로 봅니다.
  되묻기 목표(품번만 있는 입력 70%)도 57.1%로 미달했고 같은 방식으로 처리했습니다.
- ~~56.7%는 참고 자료가 5,892건일 때의 숫자입니다.~~ **해소됐습니다.**
  보통 건 20건을 빼 5,872건이 된 뒤 두 번째로 열었고, 같은 숫자가 나왔습니다.
- **실무의 실제 입력은 카탈로그 PDF나 제품 사진입니다.** 지금은 텍스트만 받습니다.
  되묻기가 걸린 뒤 사용자가 카탈로그밖에 없으면 할 수 있는 일이 없습니다.
  인용할 숫자와 배포한 시스템을 같게 두려고 봉인을 다 열 때까지 미뤘습니다.
  이제 붙인다면 **텍스트 경로 앞단**(카탈로그 → 물품설명 초안)으로 넣어야 위 숫자가
  그대로 유효합니다. 판단 경위는 [EXPERIMENTS.md](EXPERIMENTS.md)에 있습니다.
- 웹 UI는 로컬에서 동작합니다. **공개 URL 배포는 아직입니다.**

## 실행

```bash
python -m venv .venv && .venv\Scripts\activate
pip install -r requirements.txt
echo GEMINI_API_KEY=your_key > .env
```

```bash
streamlit run app.py       # 웹 UI ([0] 게이트 + [1]~[4] 분류과정)
```

```bash
python -m src.evaluate     # 평가셋 로딩·채점 로직 확인 (API 호출 없음)
python -m src.hsk          # HS부호 사전 생성·검증 (API 호출 없음)
python -m src.search       # 결정례 유사 검색
python -c "from src import evaluate; evaluate.run_rerank_batch()"   # 전체 분류과정 평가
```

앱에는 **세션 5회 / 일일 50회**의 분류 상한이 걸려 있습니다. 공개 URL에 인증이 없고
API 키가 제 것이므로 상한이 유일한 방어선입니다. 실행 기록은 SQLite 파일 하나
(`data/runs.db`)에 남고, 사용자가 입력한 물품설명 원문이 들어가므로 커밋하지 않습니다.

## 구조

```
src/
├── config.py      API 키·모델명·경로
├── llm.py         Gemini 호출 래퍼 (재시도·토큰 집계)
├── collect.py     관세법령정보포털 결정례 수집
├── search.py      임베딩 + 코사인 유사도 검색
├── hsk.py         HS부호 사전 (6자리 → 10자리 목록)
├── pipeline.py    [0] 게이트 · [1] 후보 생성 · [3] 재정렬 · [4] 세번 확정
├── evaluate.py    채점·배치 실행·일관성 측정
└── storage.py     앱 실행 기록 (sqlite3, 표준 라이브러리)

app.py             Streamlit UI. 분류과정은 부르기만 하고 측정 코드와 섞지 않는다

EXPERIMENTS.md     모든 실험의 날짜별 기록 (틀렸던 판단과 정정 포함)
CLAUDE.md          설계 원칙과 스코프 통제 규칙
```

의존성은 7개입니다. LangChain·벡터DB·웹 프레임워크를 쓰지 않았습니다 —
결정례 수천 건 규모에서는 numpy 배열 하나로 충분하고, 추상화가 두꺼우면
어디서 틀렸는지 알 수 없기 때문입니다.

### 용어 대응

이 문서는 읽기 쉬운 말을 썼습니다. 코드와 [EXPERIMENTS.md](EXPERIMENTS.md)에서는
같은 것을 다음 이름으로 부릅니다.

| 이 문서 | 코드 · EXPERIMENTS.md |
|---|---|
| 어려운 건 30건 (봉인) | 홀드아웃 / 테스트셋 (`load_testset`) |
| 보통 건 20건 (감시용) | 회귀셋 (`load_regression`) |
| 연습용 29건 | 개발셋 / 평가셋 (`load_cases`) |
| 참고하는 과거 결정례 | 검색 코퍼스 |
| 1순위 정답률 (앞 6자리) | `top1_6` |
| 후보 3개 안에 정답 | `top3_6` |
| 재정렬 전 / 후 | `before` / `after_A` |
| 맞게 바뀐 건 / 틀리게 바뀐 건 | 승격 / 강등 |
