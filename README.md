# HS코드 분류 검증 보조 시스템

수입 물품의 물품설명을 넣으면 **HS 10자리 세번 후보와 그 근거가 된 과거 결정례**를 함께 돌려주는 시스템입니다.

관세 품목분류는 같은 물품을 두고도 판단이 갈립니다. 그래서 목표를 "정확한 자동 분류기"가 아니라
**"사람이 검토할 지점을 짚어주는 보조 도구"** 로 잡았습니다.

---

## 결과

**아래는 개발 중 한 번도 보지 않은 홀드아웃 30건의 숫자입니다.**

| 지표 | baseline | 현재 |
|---|---|---|
| Top1 6자리 정확도 | 44.8% | **56.7%** |
| 10자리 정확도 | 13.8% | **50.0%** |
| 6→10자리 전환율 | 31% | **88.2%** |

baseline은 같은 물품설명을 아무 보조 없이 LLM에 그대로 물었을 때의 값입니다
(`gemini-3.1-pro-preview`, 검색 차단, 건별 새 세션, 수기 측정 29건).

> baseline 6자리는 처음 41.4%로 기록했다가 **44.8%로 정정했습니다.** 측정표의 O/X 계산에
> 셀 오류가 있어 1건이 오답으로 세어져 있었습니다. 제 개선 폭이 3.4%p 줄어드는 정정입니다.
> 경위는 [EXPERIMENTS.md](EXPERIMENTS.md)에 있습니다.

> 개발셋(29건)에서는 6자리 75.9% / 10자리 69.0%가 나왔습니다.
> **19%p 낮은 홀드아웃 숫자를 대표값으로 씁니다.** 그 격차가 왜 생겼는지는
> [EXPERIMENTS.md](EXPERIMENTS.md)에 분석해 두었습니다.

## 어떻게 동작하는가

```
물품설명
  ├─[1] 후보 생성    LLM에 6자리 후보 3개를 받는다
  ├─[2] 결정례 검색  물품설명 임베딩으로 유사 결정례 top-5 (코퍼스 5,921건)
  ├─[3] 재정렬       후보 + 결정례를 함께 주고 순위를 다시 판단
  └─[4] 세번 확정    확정된 6자리 아래 10자리 목록에서 선택
출력: 코드 + 근거 결정례 + 확신도 + 사람이 확인할 포인트
```

설계의 출발점은 baseline 측정에서 나온 사실 하나였습니다.

> **모델은 이미 정답의 86.2%를 후보 3개 안에 담고 있었다.**
> 부족한 건 생성 능력이 아니라 **순위**다.

그래서 새 코드를 만들지 않고 순위만 고치는 [3]을 1순위로 두었고, [3]에는
**후보 밖 코드를 만들지 못하게** 제약을 걸었습니다. 그래야 개선이 재정렬 덕인지
후보 확장 덕인지 구분됩니다.

[4]는 관세청 공식 HS부호 목록(11,327개)에서 6자리 하위 항목만 뽑아 선택지로 줍니다.
목록을 주기 전에는 모델이 10자리를 **지어냈습니다.**

## 이 프로젝트에서 가장 신경 쓴 것 — 측정

정확도를 올린 것보다, **올랐다는 사실을 어떻게 증명했는가**에 더 많은 시간을 썼습니다.

**개선분을 겹쳐 세지 않습니다.** 44.8% → 75.9%를 통째로 "재정렬 효과"라고 부르지 않았습니다.

| 단계 | Top1 6자리 | 순수 기여 |
|---|---|---|
| baseline | 44.8% | — |
| + 평가 자동화 · JSON 구조화 출력 | 55.2% | 프롬프트·출력형식 |
| + [3] 재정렬 | 72.4% | **+5건** |

`before`(재정렬 안 했을 때)를 **같은 실행 안에서** 함께 재기 때문에, temperature 1의
실행 간 변동이 개선분에 섞이지 않습니다.

**비율이 아니라 건별 O/X를 baseline과 대조합니다.** 비율만 같고 맞힌 건이 다를 수 있어서,
매 실행마다 회수·손실 건 번호를 출력합니다.

**홀드아웃은 2번만 엽니다.** 테스트셋 30건은 코퍼스에서 제외해 두고, 열람 횟수를
규칙으로 제한했습니다. 개발셋 숫자에 맞춰 튜닝하다 보면 그 숫자를 실력으로 착각하게 되기 때문입니다.
실제로 열어 보니 19%p 낮았습니다.

**검색 누수를 통제합니다.** 평가 대상 결정례가 검색 코퍼스에 있으면 정답을 그대로 베낍니다.
기본 동작은 제외이고, 포함 조건은 격차 측정용으로만 켭니다.

## 정확도보다 쓸모 있을지 모르는 발견

모델이 스스로 매긴 확신도가 실제 정답률을 가릅니다. **두 데이터셋에서 모두 재현됐습니다.**

| 확신도 | 개발셋 | 홀드아웃 |
|---|---|---|
| high | 19/21 (90.5%) | 17/24 (70.8%) |
| medium | 2/6 | **0/5** |
| low | 0/2 | **0/1** |

medium·low는 홀드아웃에서 **6건 전부 오답**이었습니다.
"확신도가 high가 아니면 사람이 반드시 확인" 이라는 운영 규칙의 근거가 됩니다.

또 하나, [4]는 정확도만 올린 게 아니라 **답을 재현 가능하게** 만들었습니다.

| | 이전 | 현재 |
|---|---|---|
| 6자리가 3회 일치 | 90% | 80% |
| **10자리가 3회 일치** | **60%** | **80%** |

이전에는 6자리가 같아도 10자리가 흔들렸습니다. 지금은 두 숫자가 같습니다 —
**6자리만 정해지면 10자리는 더 이상 흔들리지 않습니다.**

## 알려진 한계

- **평가 셋이 공표된 결정례입니다.** 검색 가능한 모델에서는 과대추정됩니다.
  검색을 차단해 통제했고(결정례 인용 0건 확인), 실제 타겟인 미결정 신규 품목의 대리 지표로 씁니다.
- **표본이 작습니다.** 개발셋 29건, 홀드아웃 30건입니다. 1~2건이 3%p를 움직입니다.
- **5주차 목표(6자리 60%)에 미달했습니다.** 56.7%로 1건 차이입니다.
  목표를 낮춰 기록하고 다음 단계로 넘어갔습니다 — 미달 사실과 원인 분석도 산출물로 봅니다.
- 되묻기 단계([0])와 웹 UI는 아직 없습니다.

## 실행

```bash
python -m venv .venv && .venv\Scripts\activate
pip install -r requirements.txt
echo GEMINI_API_KEY=your_key > .env
```

```bash
python -m src.evaluate     # 평가셋 로딩·채점 로직 확인 (API 호출 없음)
python -m src.hsk          # HS부호 사전 생성·검증 (API 호출 없음)
python -m src.search       # 결정례 유사 검색
python -c "from src import evaluate; evaluate.run_rerank_batch()"   # 전체 파이프라인 평가
```

## 구조

```
src/
├── config.py      API 키·모델명·경로
├── llm.py         Gemini 호출 래퍼 (재시도·토큰 집계)
├── collect.py     관세법령정보포털 결정례 수집
├── search.py      임베딩 + 코사인 유사도 검색
├── hsk.py         HS부호 사전 (6자리 → 10자리 목록)
├── pipeline.py    [1] 후보 생성 · [3] 재정렬 · [4] 세번 확정
└── evaluate.py    채점·배치 실행·일관성 측정

EXPERIMENTS.md     모든 실험의 날짜별 기록 (틀렸던 판단과 정정 포함)
CLAUDE.md          설계 원칙과 스코프 통제 규칙
```

의존성은 7개입니다. LangChain·벡터DB·웹 프레임워크를 쓰지 않았습니다 —
결정례 수천 건 규모에서는 numpy 배열 하나로 충분하고, 추상화가 두꺼우면
어디서 틀렸는지 알 수 없기 때문입니다.
